# Update MNX vendored assets

Use this skill for a controlled, evidence-based refresh of
`third_party/w3c-mnx`. The vendoring script is the source of truth for the
asset update; the skill adds the audit needed to determine whether the new
schema and examples require follow-up code or test work.

## Guardrails

- Inspect `git status --short` before doing anything. Preserve unrelated user
  changes and stop for user direction if existing changes overlap
  `third_party/w3c-mnx`.
- Confirm the upstream ref when it is not explicit. Use `main` only when the
  user requests the latest MNX/main assets.
- The vendoring script intentionally changes committed assets. Treat that as
  the only automatic mutation in this workflow. Do not modify `src/`, tests,
  or upstream example content as part of the audit.
- Keep code and test changes interactive: report proposed changes and wait for
  explicit user approval before applying them.
- Never hand-edit `mnx-schema.xxd`; it is generated by the vendoring script.

## Workflow

### 1. Establish the baseline

Record:

```sh
git status --short
cat third_party/w3c-mnx/UPSTREAM_COMMIT
jq -r '.["$id"]' third_party/w3c-mnx/mnx-schema.json
git ls-files 'third_party/w3c-mnx/examples/*.json' | wc -l
```

Read `scripts/update-w3c-mnx.sh` if its behavior is not already known. Note
the current source schema, generated header, and example count before the
update.

### 2. Run the vendoring script

For the latest upstream branch:

```sh
./scripts/update-w3c-mnx.sh main
```

For a requested commit or ref, pass that ref instead. If network access is
blocked, report the failure and request permission to retry with network
access; do not substitute a guessed commit or manually copy files.

Afterward record the new `UPSTREAM_COMMIT`, schema `$id`, and example count.
Run `git diff --check`.

### 3. Audit example changes

Use Git, not only filesystem counts, to determine what changed:

```sh
git diff --name-status -- third_party/w3c-mnx/examples
git diff --stat -- third_party/w3c-mnx/examples
git ls-files 'third_party/w3c-mnx/examples/*.json' | wc -l
find third_party/w3c-mnx/examples -maxdepth 1 -type f -name '*.json' | wc -l
```

Report separately:

- modified examples;
- added examples;
- deleted examples;
- unchanged example count;
- schema or generated-header changes unrelated to examples.

Inspect changed examples when their structure or validity could affect
mnxdom. Do not assume that a changed documentation page represents a changed
vendored JSON example.

### 4. Check schema-only examples

Read `tests/validation/test_examples.cpp` to identify the current
`kSchemaOnlyExamples` list. The test dynamically walks every vendored `.json`
file, but the schema-only list is intentionally excluded from semantic
validation.

For each schema-only example, run both schema and semantic validation without
editing the test suite. A temporary, out-of-tree harness linked against the
existing build is acceptable; remove it afterward. Alternatively use an
existing targeted test mechanism if it can invoke both validators. Capture
all semantic errors, not just the first one.

Classify each example:

- **Can become full-validation**: schema and semantic validation pass, with no
  fixture or implementation changes needed.
- **Needs fixture correction**: the example is intended to be semantically
  complete but contains fixable content errors; propose the exact upstream or
  local change and wait for approval.
- **Illustrative/schema-only by design**: it intentionally omits musical
  content or violates mnxdom whole-document invariants; leave the exemption.
- **Validator gap**: the example exposes a likely mnxdom semantic-validator
  deficiency; report it separately rather than weakening the validator.

Do not silently change `kSchemaOnlyExamples` or example JSON files.

### 5. Audit schema compatibility with mnxdom

Compare the old and new schemas after canonicalizing JSON when possible:

```sh
git show <old-commit>:docs/mnx-schema.json > /tmp/mnx-schema-old.json
jq -S . /tmp/mnx-schema-old.json > /tmp/mnx-schema-old.sorted.json
jq -S . third_party/w3c-mnx/mnx-schema.json > /tmp/mnx-schema-new.sorted.json
diff -u /tmp/mnx-schema-old.sorted.json /tmp/mnx-schema-new.sorted.json
```

Prioritize changes that affect the C++ API or validation behavior:

- added or removed properties, definitions, enum values, or literal values;
- changed property types or references;
- `minimum`, `maximum`, `exclusiveMinimum`, `minItems`, or `maxItems`;
- changed defaults described by the MNX specification;
- schema `$id`/version changes;
- constraints that conflict with existing `mnxdom` semantic checks.

### 5a. Cross-check default values

Audit defaults as a separate compatibility concern. JSON Schema `default` is
an annotation; it does not cause a validator to insert an omitted property.
The MNX API/specification may instead express defaults in reference prose or
metaspec data, and mnxdom may represent them through accessor behavior.

Search the new schema for explicit defaults:

```sh
jq '.. | objects | select(has("default"))' third_party/w3c-mnx/mnx-schema.json
```

Then search the upstream MNX API/reference sources available in the checkout
or fetched source for normative default statements, including phrases such as
`default`, `if omitted`, `if not provided`, `assumed`, and `automatically`. For
each default, record the JSON path/property, specified value, source wording
or source location, schema `default` value if present, and mnxdom accessor or
constructor behavior.

Classify every case:

- **Consistent**: schema annotation, MNX specification/API, and mnxdom behavior
  agree.
- **Schema annotation missing**: the MNX API specifies a default but the
  schema has no `default`; report it without adding one automatically.
- **mnxdom behavior missing or inconsistent**: the API default is not exposed
  by the corresponding accessor or constructor, or serialization semantics do
  not match the project convention.
- **Schema-only annotation**: the schema has a `default` with no normative MNX
  basis; flag it for specification review.
- **Ambiguous/conflicting**: sources disagree or the wording describes
  implementation-defined automatic behavior rather than a fixed value.

Check both enum defaults and scalar defaults. For enum defaults, verify enum
declaration order, `EnumerationMaps.cpp`, and
`MNX_OPTIONAL_PROPERTY_WITH_DEFAULT`. For scalar defaults, inspect the
corresponding property macro and whether the default should be omitted from
serialized JSON. If upstream currently has no schema `default` keywords,
explicitly report that fact and still record prose/API defaults as a baseline
for future updates.

Trace each relevant schema change into `src/` with searches for the JSON key,
enum, property macro, constructor, enum mapping, and validator logic. Check
both serialization and deserialization. In particular, an enum whose first
value is the MNX default should have a matching entry in
`src/EnumerationMaps.cpp`, and an omitted property with a specified default
should generally use `MNX_OPTIONAL_PROPERTY_WITH_DEFAULT`.

Report compatibility findings as one of:

- compatible and already represented;
- schema-only behavior change handled by final validation;
- API mismatch or loss of representability;
- semantic-validator mismatch;
- unresolved specification question.

Do not change source code during this audit. Present file/line locations and
the smallest proposed follow-up for user approval.

### 6. Verify and report

If the user authorized the vendored asset refresh, rebuild and run the
available suite after the update:

```sh
cmake --build build
ctest --test-dir build --output-on-failure
```

If the build directory is absent or dependencies would need to be fetched,
report that rather than silently changing package/build configuration.

Finish with:

1. old and new upstream commits and schema IDs;
2. exact changed files and example additions/modifications/deletions;
3. schema-only example semantic results and recommendation for each;
4. compatibility findings with source locations;
5. tests and checks run;
6. any proposed code or test changes awaiting approval.

Never claim that an update is complete while a failed vendoring command,
unreviewed generated file, or unclassified example change remains.
